# BatchTrade 0.1.2：原始交易槽与解析缓存的勘误

检查日期：2026-11-03。本文只报告客户端 PE、公开结构声明与插件代码的静态复核，没有执行交易、调用游戏方法或采集故障当时的内存。文内不包含客户端二进制、账号、角色信息或个人安装路径。

## 结论与上一版错误

0.1.1 的 `OfferSourceLinksMatch` 把 `InventoryManager.TradeItemsLocal` 当作仍保留符号链接的原始交易槽，要求其中的非空物品 `IsSymbolic == true`。这个要求不符合本客户端正常玩家交易的缓存更新流程。

[上一版证据](batchtrade-native-evidence-v011.md)“放入交易槽与数量窗口的先后关系”一节只跟踪了 `RVA 0x87CDD0` 中的字段复制，漏掉了它调用的 `InventoryContainer.GetInventorySlot` 的解析行为。原文把“复制输入对象的 IsSymbolic/联合字段”推导为“保留容器 2005 原始槽的符号链接”，这个推导错误，应以本文为准。

准确流程是：原始交易槽保存源背包链接和交易数量；`GetInventorySlot` 返回解析后的源背包物品；`0x87CDD0` 把该源物品身份复制到本地缓存，再从原始交易槽单独取交易数量写入缓存。因此，在正常源背包物品不是符号链接时，本地缓存是 **`IsSymbolic == false`、真实物品 ID/品质、交易数量**。

用户截图的汇总错误覆盖多个校验条件，截图本身不能证明当时每个字段的值。静态代码足以确认上述缓存链接校验会拒绝正常路径，也与该报错位置一致；这不是故障现场内存采样或真实交易通过证明。

## 1. 容器取格函数先解析链接

容器初始化函数 `RVA 0x869980` 在 `0x8699BB` 取 vtable `0x21943B0`，并在 `0x8699D0` 给常规容器数组逐项安装该表。该表 vfunc 5 为 `RVA 0x869330`。

`0x869330` 的关键步骤：

| RVA | 行为 |
| --- | --- |
| `0x869334`–`0x86935B` | 取得 `Items`，检查数组非空、索引非负且小于 `Size`。 |
| `0x869364`–`0x86936E` | 计算原始元素地址 `Items + index * 0x48`，检查其 `IsSymbolic`。 |
| `0x869374` | 非符号元素直接返回原始元素地址。 |
| `0x869381`–`0x86938C` | 符号元素从 `LinkedInventoryType` 取得源容器。 |
| `0x869391`–`0x8693A6` | 取得 `LinkedItemSlot`，检查源数组及索引。 |
| `0x8693AD`–`0x8693B1` | 返回源容器 `Items + linkedSlot * 0x48`，并非原始交易槽地址。 |

这里没有先制造一个临时副本；它直接返回链接源的地址。因此，**要读取容器 2005 的原始链接与本槽数量，必须读取 `container->Items[index]`，不能调用 `container->GetInventorySlot(index)`。** 2005 在公开枚举中名为 `HandIn`，也被玩家交易路径复用，只有已经验证属于本次玩家交易时才能解释为交易工作槽。

## 2. 本地缓存组合身份与数量

`RVA 0x87CDD0` 是本次玩家交易本地槽的读取/刷新路径：

| RVA | 行为 |
| --- | --- |
| `0x87CDE7` | 只接受物品索引 `0..4`。 |
| `0x87CDF1`–`0x87CDF6` | 取得容器 `2005 (0x7D5)`。 |
| `0x87CE07`–`0x87CE1C` | 调用容器 vfunc 5；返回值已按上节解析。 |
| `0x87CE20`–`0x87CE2E` | 计算缓存地址 `InventoryManager + 0x1E18 + index * 0x48`，没有压紧或重排索引。 |
| `0x87CE32`–`0x87CED4` | 将返回对象的字段复制到缓存，包括源背包的 Container/Slot、IsSymbolic、ID、品质等。 |
| `0x87CEE3`–`0x87CF01` | **另行直接读取原容器 `Items` 数组**，计算该交易槽的原始地址。 |
| `0x87CF05`–`0x87CF10` | 调用原始槽 `GetQuantity`，再调用缓存的 `SetQuantity`，将缓存数量修正为交易数量。 |

因此缓存不是原始工作槽的整体镜像。缓存的 Container/Slot 也可能是源背包坐标，不能要求它们为容器 2005 和交易格序号。

这条路径没有调用 `InventoryItem.Copy` vfunc 1。该方法的公开注释虽提到解析符号链接，却不是本次解析发生的位置；本次解析发生在容器 vfunc 5。

`AgentTrade` 的菜单处理 `RVA 0xCF4990` 从索引 0 开始，依次调用上述本地槽读取函数，并按 `GetItemId() == 0` 选择第一个空位置，最多五格；`0xCF4A46` 把该索引作为目标格交给 `MoveItemSlot`。未发现该路径存在从 1 开始的格号或缓存压紧逻辑。

## 3. 仍然成立的数量时序

上一版关于先创建链接、暂设数量 1、源堆大于 1 才创建数量弹窗的结论，仍由相应独立调用链支持：

- `0x8712BD` 给原始交易槽设置源链接；`0x8712CD` 设置其数量为 1。
- `0x86E08A`–`0x86E096` 检查源数量，大于 1 才进入数量弹窗路径。
- 数量提交处理在 `0x88716B` 对原始交易槽设置输入数量。
- 原始槽 `GetQuantity`（vfunc 12，`0x868940`）在符号链接情况下返回本槽数量与源数量的较小值。
- `SetQuantity`（vfunc 13，`0x8689B0`）写本槽数量；数量为 0 且元素仍为符号链接时，并不清除链接联合字段。因此“数量为 0”与“解析后物品 ID 必须为 0”不能不加区分地混为一个规则。是否允许某个过渡状态，还需结合本次原始槽、阶段和窗口归属判断。

源堆大于 1、计划量为 1 时，也必须完成本次应有的数量窗口，不能把原生临时数量 1 当成已提交。原始槽在回调中改变后，缓存须等其刷新路径执行才反映新的量；读取规则必须区分等待同步和已证实的内容变化，最终提出/确认交易仍需完整一致。

## 实现约束与验证边界

建议分别捕获三种视图，并给不匹配项提供独立错误码：

1. **原始工作槽**：受本次 Trade 指针/代次、伙伴、双方状态保护，检查容器 2005 的 `Items != null`、`Size >= 5`，仅读前五格；使用真实数组元素检查符号链接与冻结源背包坐标。
2. **原源背包槽**：检查物品 ID、HQ 和原源数量仍符合冻结计划，避免链接指向发生变化的物品。
3. **解析缓存**：用来核对实际呈现的物品身份和交易数量，不再要求其保留符号链接；准备提出交易与最终确认时，要求缓存和工作槽都与完整计划一致。

数量回调之后的预期缓存滞后可以有界等待；不允许以“等待同步”为由忽略新增物品、换源、远端物品/金币变化或最终确认前的不一致。缓存的第六格用于金币，不能仅据此假设容器 2005 的第六格也是金币；原始工作槽读取范围应限制为已经核实的前五格。

原先数量/最终弹窗接收者、EventKind、文本与异步 Setup 的静态证据未因本次发现而改变。本文不证明所有其他运行边界都已正确，也不把构建或纯规则测试等同于真实玩家交易通过。
