# 批量物品交易（BatchTrade）

独立 Dalamud API 15 插件，向开始时选定的玩家分批赠送一种物品，对方逐笔手动确认。使用 `/batchtrade` 打开设置，`/batchtrade stop` 停止任务。插件加载后默认空闲，不自动恢复上次任务。

**0.1.3.0 仅适配国服客户端 `2026.10.06.0000.0000`。** 已通过编译和 160 项离线规则检查；本版完整游戏交易流程仍待验证。运行时不依赖 DailyRoutines、OmenTools、Artisan 或 AutoRetainer。

## 数量与使用

选择背包物品、HQ/NQ、总数量和每格数量上限，然后选中接收玩家并点击开始。每格上限可填 **1–999，默认 999**；每笔最多占 5 个物理格，五格都能放 999 时一笔最多送出 4,995 个。物品本身的堆叠限制也会参与规划。

例如背包已有 518、999、999 三堆，总量 2,516、每格上限 999，会按 **999、999、518 在同一笔完成**。已有 999、999、999、262 四堆时，总量 3,259 也只需一笔。每笔优先选择数量较多的原背包堆，同量时按背包页和槽位排序；每个源格在一笔中最多使用一次，不自动拆堆，也不把同一源格的剩余物品反复放进多个交易格。

每格上限为 99 时，三个可用源堆可在同一笔各放最多 99；上限为 1 时，可从五个不同源格各放 1。只有一个源格时，每笔也只使用这一格。第六个源堆留到下一笔，成功结算后重新读取背包并规划。旧版保存的上限数值会迁移为每格上限，十项延迟保留原设置。

双方实体、姓名、世界、物品品质、总数量和所有时间参数在开始时固定。界面只显示游戏线程发布的快照，执行时会再次核对目标；更改目标不会改为给另一名玩家发送。配置只保存物品、数量和时间设置，不保存角色身份。

## 各步骤延迟

展开“各步骤延迟（毫秒）”分别调整。每个动作都等自己的延迟，并核对上一动作的实际结果；正常发送和取消都受每个框架帧最多一次、至少间隔 100 毫秒的限制。

| 设置 | 默认值 | 可填范围 |
| --- | ---: | ---: |
| 启动延迟 | 1000 ms | 0–600000 ms |
| 发起交易前 | 800 ms | 100–30000 ms |
| 打开物品菜单前 | 500 ms | 100–30000 ms |
| 选择交易菜单项前 | 500 ms | 100–30000 ms |
| 提交物品数量前 | 800 ms | 100–30000 ms |
| 关闭自身菜单／下一格前 | 500 ms | 100–30000 ms |
| 提出交易条件前 | 800 ms | 100–30000 ms |
| 最终确认交易前 | 1000 ms | 100–30000 ms |
| 取消当前交易前 | 300 ms | 100–30000 ms |
| 两笔交易间隔 | 1500 ms | 0–600000 ms |

界面显示当前步骤倒计时。上述人为延迟不占用每笔等待超时；等待对方或游戏响应的默认预算为 90 秒。长启动延迟和两笔间隔没有额外的 10 秒总超时。延迟期间仍持续检查目标、金币、背包、已放入物品和窗口是否变化。

停止会立即撤销尚未发送的步骤；最终确认前，只有原交易窗口、生命周期和双方身份仍匹配时，才在安全间隔后发送一次取消。结算阶段只停止后续批次，不再代取消已经提交的交易。卸载也不会跳过延迟；如果来不及安全取消，会记录需手动取消当前交易。关闭设置窗口仅隐藏界面，运行任务可用停止命令终止。

## 0.1.2 交易格校验修正与诊断

0.1.1 把本地交易缓存当成仍然包含源背包链接的工作格，因此正常缓存中的物品也会触发“待填交易格或此前已填物品格被修改”。静态核查确认，容器的 `GetInventorySlot` 会展开符号链接；本地缓存复制的是展开后的物品，再单独保存交易数量。

0.1.2 直接读取交易工作容器 `HandIn.Items` 的前五格，核对源链接、原背包物品、品质及数量；缓存只用于核对同步后的交易值。工作格尚未建立时不会提交数量，缓存尚未追上工作格时只等待。提出条件和最终确认前，每次都要求工作格、缓存逐格一致且同步标志已清除。缓存中数量为零但残留物品 ID 按空格处理；工作格残留源链接则继续等待，不能据此授权下一步。

停止原因现在包含具体检查码和物理槽号。“复制最后诊断”可复制插件/游戏版本、阶段、计划、工作格、缓存、源物品格、同步标志及数量提交状态；每次任务停止只记录一次。诊断不包含玩家姓名、实体 ID、内存地址或全部背包。卸载时只使用已有快照，不为诊断重新读取游戏状态。

[0.1.2 原生核查与前版勘误](https://github.com/Houraiji9/FFXIV-StandalonePlugins/blob/main/docs/batchtrade-native-evidence-v012.md)记录了本次修正依据。十项延迟和原有三信号结算规则保持不变。

## 数量窗口与版本适配

0.1.0 把数量窗回调接收者限定为 `AgentTrade`，与当前客户端的真实流程不符；它还在 `PostSetup` 中立即要求映射已经注册。新版先捕获本次交易菜单操作对应的新窗口，将归属校验延后到后续框架帧，再核对真实接收者、事件种类、源物品格、接收玩家和数量范围。

当前版本的数量窗接收者是 `InventoryManager` 内嵌接口 `+0x3708`，最终交易确认接收者是 `+0x36E8`，普通物品路径的事件种类均为 0。适配代码只比较这些已核实的指针归属，不解引用未公开字段，也不调用手写原生函数。客户端版本缺失、版本变化或 SDK 结构大小不符时拒绝运行。

游戏工作槽是指向源背包格的符号链接，打开数量窗前会先显示临时数量 1。新版分别读取工作格链接与合法源背包格的公开字段，不把缓存当链接，也不在未知链接上调用原生 getter。源堆大于 1 时，必须完成本次数量提交后才认定已放入，即使计划数量恰好也是 1。数量窗最大值无需等于源堆数量，但实际提交量必须同时满足窗口范围、源库存、物品堆叠和当前格上限，并与本次任务的计划量一致；第二、第三格不会扣减前面已放入的数量额度。

[原生调用与版本适配证据](https://github.com/Houraiji9/FFXIV-StandalonePlugins/blob/main/docs/batchtrade-native-evidence-v011.md)记录了静态核查链。数量提示按游戏 Addon 206 读取，支持 `ConstString` 和纯文本规范化。失败状态区分窗口替换、菜单代次、源格、归属、提示及范围，便于定位下一次反馈。

## 保护规则与验收边界

- 只发送指定物品与品质，双方金币必须为零；对方放入其他内容立即停止，不自动接受传入交易。
- 只用普通背包四页；不自动交易不可交易物品、已有精炼度/收藏价值的格或镶嵌魔晶石的装备。
- HQ 指物品品质选择；它走已核实的普通数量和最终确认流程。任何额外确认窗口都会停止，不自动点击 NPC 交纳等无关提示。
- 取消、超时、掉线、身份/距离变化、非预期物品或背包变动都会停止。结果不明的交易不会重发。
- 只有 **送出物品日志 10920、所选物品库存精确减少本笔数量、原交易已经结束** 三项全部到齐才计入进度。三项顺序不限，允许逐槽扣减；首次结算信号后最多核对 5 秒。窗口关闭或任务空闲本身不是成功。

已有源码和原生静态证据不替代游戏验收。本版仍需验证五格、末格部分数量、HQ、对方取消/修改内容及网络延迟的完整流程。首次可用少量物品，若停止先核对实际背包，再决定是否重新开始。同一交易窗口应只由一个自动化流程控制。

## 构建与测试

在仓库根目录执行，SDK 获取方法见根说明：

```powershell
dotnet build plugins/BatchTrade/BatchTrade.csproj -c Release
dotnet run --project tests/BatchTrade.Tests/BatchTrade.Tests.csproj -c Release
```

160 项检查覆盖三信号全部顺序、取消/库存异常、2,516 三格一笔和 4,995 五格一笔、每格 1/99/999 上限、源格排序与去重、第六堆留到下一笔、跨背包源链接、旧配置迁移、HQ/部分数量、临时数量 1、已填槽变化、版本/接收者/事件种类与范围、独立步骤延迟、重复调度幂等、同帧与 100 ms 限速、停止撤销和长间隔。双视图回归继续覆盖空工作格不能授权数量、源链接错误、缓存延迟/回退、零数量残留和具体诊断码。测试不连接游戏。
